第 11 章

用 LLM 做产品

技术都讲完了，剩下最难的问题：这东西该长什么样？过去几十年的软件交互范式建立在「计算机绝对可靠」这个前提上，而 LLM 恰好把这个前提拿掉了。

读完这一章你会

  • 理解为什么传统的「工具面板 + 画布」范式不完全适用于 LLM 应用
  • 说清楚聊天助手、协同编辑、环境计算三种范式的差别
  • 知道每种范式需要前面哪几章的能力做支撑

被动摇的前提

看看 Figma 或 Word 的界面，它们都是同一个结构：

  • 一个工具面板：线条、形状、表格、标题、拼写检查……
  • 一块画布：你把这些积木摆上去，组成作品。

这个结构隐含一个假设：软件能做什么，在界面设计的时候就已经确定了。对 Figma 成立——所有工具都是工程师提前写好的。

但对重度使用 LLM 的软件不成立。而且 LLM 还带来了一个反向的性质：它对「输入不精确」非常宽容（打错字、说半句、表述含糊都行），代价是输出有时也「不太精确」。而过去几十年的 HCI 设计，全是围绕「输入精确、输出必然精确」建立的。

三种范式

书里给了三个可能的答案。它们最大的区别在于人和 LLM 是否同时在工作。

范式一：聊天助手

最容易加到现有产品上的一种：在侧边栏挂一个 AI，主要工作还是在原界面里做。GitHub Copilot Chat 就是典型。

进阶版是让侧边栏和主界面互相打通：助手能「看见」你当前打开的文件或选中的文本，也能反过来往编辑器里插入或修改内容。这就从「问答」变成了「协作」的雏形。

需要的能力为什么对应章节
聊天模型对话微调让它天然适合多轮交互第 1 章
对话历史不能「过不了打招呼」——后续提问都会引用前文第 4 章
流式输出逐 token 显示，抵消 LLM 的固有延迟第 8 章
工具调用把「读取选中文本」「在文末插入」暴露成工具，助手才能操作主界面第 6 章
人在环路一旦它能改画布，就必须让用户能先确认、能编辑第 8 章

书里的一句提醒

流式聊天是今天最典型的 LLM 应用形态，几乎所有人第一个做的都是它。但作者猜测：它也可能变成 LLM 时代的「命令行」——最接近底层、最强大，但最终会变成小众入口，就像命令行之于今天的计算机。

范式二：协同编辑

把 LLM Agent 当成文档的另一个协作者，和人一起在同一份文档上工作。形态可以是「随时给你补全下一句的副驾」，也可以是「你派它去查资料，过一会儿它带着一节草稿回来」。

这是三种范式里工程难度最高的，因为它要求解决真正的并发问题：

要素 1

共享状态

人和 Agent 必须能读同一份文档，并产出同一种格式的编辑操作。

要素 2

任务管理器

一次有意义的编辑往往是多步、耗时、可能中途失败的。需要排队、重试、可取消。

要素 3

分支合并

你派活之后还在继续改文档。Agent 的产出要么像 Git 一样让你手动合，要么用 CRDT / OT 自动合。

要素 4

并发控制

打断、取消、改派、追加——第 8 章 double texting 那几种策略在这里全都用得上。

要素 5

撤销 / 重做栈

生产力软件的标配。人会反悔，AI 的编辑也必须能一步步退回去。

要素 6

中间输出

一句一句地出，比憋十分钟一次性甩十段更容易合并，也更容易叫停。

范式三：环境计算

「后台一直开着，发现值得你关注的事才出声」——股价提醒、Google 快讯、运维告警都是这个模式。

它一直没能普及，卡在一个地方：「什么算有意思」这件事很难提前定义清楚。要么规则太死用不上，要么要花大量时间配置规则，得不偿失。

LLM 的推理能力恰好能补上这一环——它可以在运行时判断「这条信息对这个人现在是否重要」，而不需要你穷举规则。

需要的能力为什么对应章节
触发器要有持续或周期性的新信息源，否则「环境计算」无从谈起第 9 章 Cron / Webhook
长期记忆「新」是相对于「已知」而言的；没有记忆就无法判断新旧第 4 章的持久化
反思「什么算有意思」要从每次结果里学，写回长期记忆第 7 章
摘要输出后台跑一天产出的量远超人愿意看的量第 5 章的链
任务管理器长期运行必然要处理排队、失败、重试第 9 章 Platform

全书收尾

作者最后一段话值得原样带走：

这里没有捷径。你真的得先做一个粗糙的东西出来，去跟用户聊，然后不断重复，直到某个新的、意料之外的东西从另一头冒出来。

回过头看这 11 章，它们其实是一条从「模型只会说话」到「用户可以放心用的产品」的路：

章节解决的问题留下的能力
