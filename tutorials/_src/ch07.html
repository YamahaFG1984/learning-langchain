第 07 章

Agent 进阶：反思与多智能体

给 Agent 加两样人类团队才有的东西：一个会挑刺的审稿人，和一群各有专长的同事。外加实现这两者都要用到的技术底座——子图。

读完这一章你会

  • 实现「生成—反思」循环，并理解它为什么要做角色对调这个小把戏
  • 用两种方式把子图接进父图，知道各自适用于什么情况
  • 说清楚四种多智能体拓扑的差别，并实现其中的 Supervisor 架构

反思：让模型给自己挑刺

反思（也叫自我批评）就是在创作者和审稿人两个提示之间来回。这和人写东西的过程一模一样：写初稿 → 被审 → 改 → 再审。

用卡尼曼的话说，这是在用系统 2（慢、审慎）去修正系统 1（快、直觉）的产物。

ch7/{py,js}/a-reflection 
from typing import Annotated, TypedDict

from langchain_core.messages import AIMessage, BaseMessage, HumanMessage, SystemMessage
from langchain_openai import ChatOpenAI
from langgraph.graph import END, START, StateGraph
from langgraph.graph.message import add_messages

model = ChatOpenAI(model="gpt-4.1-mini")


class State(TypedDict):
    messages: Annotated[list[BaseMessage], add_messages]


generate_prompt = SystemMessage(
    "你是写作助手，负责写出优秀的三段式文章。"
    "如果用户提出批评，请给出修改后的版本。"
)

reflection_prompt = SystemMessage(
    "你是批改作文的老师。针对用户交上来的文章给出批评和改进建议，"
    "包括长度、深度、文风等方面的具体要求。"
)


def generate(state: State) -> State:
    return {"messages": [model.invoke([generate_prompt] + state["messages"])]}


def reflect(state: State) -> State:
    # 把历史里的 AI/Human 角色对调，让模型以为自己在批改「别人」的文章
    cls_map = {AIMessage: HumanMessage, HumanMessage: AIMessage}
    # 第一条是用户最初的任务描述，保持原样
    translated = [reflection_prompt, state["messages"][0]] + [
        cls_map[msg.__class__](content=msg.content) for msg in state["messages"][1:]
    ]
    answer = model.invoke(translated)
    # 批评意见伪装成「用户的反馈」返回
    return {"messages": [HumanMessage(content=answer.content)]}


def should_continue(state: State):
    if len(state["messages"]) > 6:      # 3 轮 × 每轮 2 条消息
        return END
    return "reflect"


builder = StateGraph(State)
builder.add_node("generate", generate)
builder.add_node("reflect", reflect)
builder.add_edge(START, "generate")
builder.add_conditional_edges("generate", should_continue)
builder.add_edge("reflect", "generate")

graph = builder.compile()
async function reflect(state) {
  // 角色对调
  const clsMap = { ai: HumanMessage, human: AIMessage };
  const translated = [
    reflectionPrompt,
    state.messages[0],
    ...state.messages.slice(1).map((msg) => new clsMap[msg.getType()](msg.content)),
  ];
  const answer = await model.invoke(translated);
  return { messages: [new HumanMessage({ content: answer.content })] };
}

function shouldContinue(state) {
  return state.messages.length > 6 ? END : 'reflect';
}

const graph = new StateGraph(annotation)
  .addNode('generate', generate)
  .addNode('reflect', reflect)
  .addEdge(START, 'generate')
  .addConditionalEdges('generate', shouldContinue)
  .addEdge('reflect', 'generate')
  .compile();

两个设计细节

为什么在 generate 之后判断结束？直觉上应该「批评完再改一版就结束」。这里正是这样：循环固定跑 3 轮，最后一轮的修改做完才退出，所以出口挂在 generate 上，而不是 reflect。

能不能让模型决定停？能。把 should_continue 换成「让 reflect 判断还有没有意见」即可。固定轮数的好处是延迟和成本可控。

强烈推荐的变体：用真实反馈代替 LLM 批评

如果你在写代码生成 Agent，在 reflect 之前插一个节点，把生成的代码扔给 linter 或编译器跑一遍，把真实的报错当作批评输入。只要你的领域存在这种客观校验器，就一定要用上——它比让 LLM 自己找茬可靠得多。

子图

子图就是「被当成节点用的图」。三个用途：搭多智能体系统、复用一组节点、让不同团队各管一块。

接法有两种，选哪种只取决于父图和子图的状态结构是否共享字段：

ch7/{py,js}/b-subgraph-direct · c-subgraph-function 
# ── ① 直接接：foo 是共享键 ───────────────────────────────
class State(TypedDict):
    foo: str                    # 与子图共享


class SubgraphState(TypedDict):
    foo: str                    # 与父图共享
    bar: str                    # 子图私有


def subgraph_node(state: SubgraphState):
    return {"foo": state["foo"] + "bar"}


subgraph_builder = StateGraph(SubgraphState)
subgraph_builder.add_node("subgraph_node", subgraph_node)
subgraph_builder.add_edge(START, "subgraph_node")
subgraph = subgraph_builder.compile()

builder = StateGraph(State)
builder.add_node("subgraph", subgraph)          # ← 编译后的图直接当节点
builder.add_edge(START, "subgraph")
graph = builder.compile()

print(graph.invoke({"foo": "hello"}))       # {'foo': 'hellobar'}


# ── ② 包函数：完全没有共享键 ─────────────────────────────
class SubgraphState2(TypedDict):
    bar: str                    # 都不共享
    baz: str


def node(state: State):
    response = subgraph2.invoke({"bar": state["foo"]})   # 进：foo → bar
    return {"foo": response["bar"]}                       # 出：bar → foo


builder.add_node("node", node)                # ← 注意是函数，不是子图

书里代码的一个疏漏

原书子图示例没有写 subgraph_builder.add_edge(START, "subgraph_node")，编译时会报 Graph must have an entrypoint。仓库里已经补上了。任何图（包括子图）都必须有一条从 START 出发的边。

多智能体：四种拓扑

当单个 Agent 出现这些症状时，就该考虑拆了：工具太多选不准、上下文复杂到跟不上、某个子领域需要专门的处理方式。

实现 Supervisor 架构

监督者节点做的事很简单：看完整个对话历史，用结构化输出选出下一个该干活的人，或者宣布 FINISH。

ch7/{py,js}/d-supervisor 
from typing import Literal

from langchain_openai import ChatOpenAI
from langgraph.graph import END, START, MessagesState, StateGraph
from pydantic import BaseModel

agents = ["researcher", "coder"]      # 名字必须自解释！模型只看得到名字


class SupervisorDecision(BaseModel):
    """下一个该谁干，或者 FINISH。"""

    next: Literal["researcher", "coder", "FINISH"]


model = ChatOpenAI(model="gpt-4.1", temperature=0)
supervisor_model = model.with_structured_output(SupervisorDecision)


class AgentState(MessagesState):
    next: str                        # 存放路由决策


def supervisor(state: AgentState) -> dict:
    messages = [
        {"role": "system", "content": system_prompt_part_1},
        *state["messages"],
        {"role": "system", "content": system_prompt_part_2},
    ]
    decision = supervisor_model.invoke(messages)
    # 节点必须返回「状态更新」，所以要把决策包进 next 字段
    return {"next": decision.next}


def route(state: AgentState) -> Literal["researcher", "coder", "__end__"]:
    return END if state["next"] == "FINISH" else state["next"]


builder = StateGraph(AgentState)
builder.add_node("supervisor", supervisor)
builder.add_node("researcher", researcher)
builder.add_node("coder", coder)

builder.add_edge(START, "supervisor")
builder.add_conditional_edges("supervisor", route, ["researcher", "coder", END])
builder.add_edge("researcher", "supervisor")
builder.add_edge("coder", "supervisor")

graph = builder.compile()
import { z } from 'zod';
import {
  StateGraph, Annotation, MessagesAnnotation, START, END,
} from '@langchain/langgraph';

const SupervisorDecision = z.object({
  next: z.enum(['researcher', 'coder', 'FINISH']).describe('下一个该谁干，或 FINISH'),
});

const supervisorModel = model.withStructuredOutput(SupervisorDecision);

const StateAnnotation = Annotation.Root({
  ...MessagesAnnotation.spec,
  next: Annotation(),
});

const supervisor = async (state) => {
  const decision = await supervisorModel.invoke([
    { role: 'system', content: systemPromptPart1 },
    ...state.messages,
    { role: 'system', content: systemPromptPart2 },
  ]);
  return { next: decision.next };
};

const graph = new StateGraph(StateAnnotation)
  .addNode('supervisor', supervisor)
  .addNode('researcher', researcher)
  .addNode('coder', coder)
  .addEdge(START, 'supervisor')
  .addConditionalEdges(
    'supervisor',
    (state) => (state.next === 'FINISH' ? END : state.next),
    ['researcher', 'coder', END]
  )
  .addEdge('researcher', 'supervisor')
  .addEdge('coder', 'supervisor')
  .compile();

书上代码的两处问题（仓库已修）

  1. supervisor 节点直接返回了模型输出。节点必须返回状态更新字典，所以要写成 {"next": decision.next}。
  2. "FINISH" 不是一个节点名，条件边直接返回它会报「找不到节点」。要映射成 END。

工人名字必须自解释

提示词里只会出现 ["researcher", "coder"] 这样的名字。如果叫 agent_1 / agent_2，LLM 完全没有依据做选择。名字起不好就在提示里补一段每个工人的能力描述。

小结

记住这个

反思 = 生成 ↔ 批评 + 角色对调

对调是为了迎合对话微调模型的「人—AI 交替」节奏。

记住这个

有客观校验器就别用 LLM 批评

编译器、linter、测试的报错比 LLM 自评可靠得多。

记住这个

子图接法看共享键

有共享键直接当节点；没有就包一层做状态转换。

记住这个

先别急着上多智能体
