第 10 章

测试：评估、监控与持续改进

传统软件的测试要求 100% 通过。LLM 应用做不到——同一个输入两次结果可能不同。所以测试的目标从「是否正确」变成了「相比上一版有没有变差」。

读完这一章你会

  • 用「设计 → 预生产 → 生产」三阶段框架安排测试工作
  • 实现自纠正 RAG：让应用在出错前自己发现并修正
  • 建数据集，选对评估器（启发式 / 人工 / LLM 裁判）
  • 用三个粒度评估 Agent：最终回答、单步决策、完整轨迹

三个阶段构成一个闭环

设计阶段：自纠正 RAG

朴素 RAG 有两个失败点：检索到的东西不相关，以及模型基于正确材料还是编。自纠正 RAG 在每一环后面加一个「打分员」，不合格就回退重来。

ch10/{py,js}/retrieve-and-grade · search-graph 
from langchain_core.prompts import ChatPromptTemplate
from langchain_openai import ChatOpenAI
from pydantic import BaseModel, Field


class GradeDocuments(BaseModel):
    """对检索到的文档做二元相关性打分。"""

    binary_score: str = Field(description="文档与问题是否相关，'yes' 或 'no'")


llm = ChatOpenAI(model="gpt-4.1-mini", temperature=0)
structured_llm_grader = llm.with_structured_output(GradeDocuments)

grade_prompt = ChatPromptTemplate.from_messages([
    ("system", "你在评估一份检索到的文档与用户问题的相关性。"
               "只要文档包含相关关键词或语义，就算相关。给出 'yes' 或 'no'。"),
    ("human", "检索到的文档：\n\n {document} \n\n 用户问题：{question}"),
])

retrieval_grader = grade_prompt | structured_llm_grader


def grade_documents(state):
    filtered_docs, web_search = [], "No"
    for d in state["documents"]:
        score = retrieval_grader.invoke(
            {"question": state["question"], "document": d.page_content}
        )
        if score.binary_score == "yes":
            filtered_docs.append(d)
        else:
            web_search = "Yes"          # 只要有一条不相关，就触发兜底路径
    return {"documents": filtered_docs, "question": state["question"], "web_search": web_search}


def decide_to_generate(state):
    return "transform_query" if state["web_search"] == "Yes" else "generate"
import { z } from 'zod';

const GradeDocuments = z.object({
  binary_score: z.string().describe("文档与问题是否相关，'yes' 或 'no'"),
});

const retrievalGrader = gradePrompt.pipe(llm.withStructuredOutput(GradeDocuments));

const gradeDocuments = async (state) => {
  const filteredDocs = [];
  let webSearch = 'No';
  for (const doc of state.documents) {
    const score = await retrievalGrader.invoke({
      question: state.question,
      document: doc.pageContent,
    });
    if (score.binary_score === 'yes') filteredDocs.push(doc);
    else webSearch = 'Yes';
  }
  return { documents: filteredDocs, question: state.question, webSearch };
};

合成数据

用 LLM 批量生成。补覆盖面快，但质量参差，要抽检。

LangSmith 里数据集有三种类型：kv（任意键值对，最通用，默认选它）、llm（单个 prompt / completion 字符串）、chat（序列化的消息列表）。

三类评估器

成对比较（pairwise）

「A 和 B 哪个更好」比「给 A 打几分」容易得多——对人和对 LLM 都是。LangSmith 原生支持成对评估：定义一个比较用的裁判提示，跑两个版本，直接看谁赢。适合「更详细」「更安全」这类难以量化的标准。

回归测试：这一版有没有变差

AI 应用会因为模型漂移（提供商更新模型、数据分布变化）而性能波动。所以：

  • 跟踪趋势而非绝对分数。90% 不一定是好，从 95% 掉到 90% 一定是问题。
  • 逐条对比。总分持平也可能是「修好了 5 条、弄坏了 5 条」。LangSmith 的对比视图会把相对基线变好和变差的样例分别高亮出来。
  • 设定基线版本。每次改动都和它比，而不是和上一次比。

评估 Agent：三个粒度

Agent 难评估，因为每次运行的轨迹都可能不同：调的工具不一样、步数不一样、甚至可能陷入死循环。所以要分三层看。

ch10/{py,js}/agent-evaluation-sql 
from langsmith.evaluation import evaluate
from langsmith.schemas import Example, Run

EXPECTED = ["sql_db_list_tables", "sql_db_schema",
            "sql_db_query_checker", "sql_db_query", "check_result"]


def find_tool_calls(messages):
    return [tc["name"] for m in messages["messages"] for tc in getattr(m, "tool_calls", [])]


# ② 单步：第一个工具调用对不对
def check_specific_tool_call(root_run: Run, example: Example) -> dict:
    response = root_run.outputs["response"]
    try:
        tool_call = getattr(response, "tool_calls", [])[0]["name"]
    except (IndexError, KeyError):
        tool_call = None
    return {"key": "single_tool_call", "score": int(tool_call == "sql_db_list_tables")}


# ③ 轨迹（宽松）：该调的都调了，顺序不论
def contains_all_tool_calls_any_order(root_run: Run, example: Example) -> dict:
    tool_calls = find_tool_calls(root_run.outputs["response"])
    return {"key": "multi_tool_call_any_order",
            "score": int(set(EXPECTED) <= set(tool_calls))}


# ③ 轨迹（严格）：顺序也要对（允许中间插入别的调用）
def contains_all_tool_calls_in_order(root_run: Run, example: Example) -> dict:
    tool_calls = find_tool_calls(root_run.outputs["response"])
    it = iter(tool_calls)      # 用同一个迭代器逐个找，就是子序列判定
    return {"key": "multi_tool_call_in_order",
            "score": int(all(e in it for e in EXPECTED))}


experiment_results = evaluate(
    predict_sql_agent_messages,
    data="sql-agent-response",
    evaluators=[contains_all_tool_calls_any_order, contains_all_tool_calls_in_order],
    num_repetitions=3,          # 重复多次，抵消随机性
    experiment_prefix="sql-agent-gpt41-trajectory",
)
function findToolCalls({ messages }) {
  return messages.flatMap((m) => m.tool_calls?.map((tc) => tc.name) || []);
}

function containsAllToolCallsAnyOrder(rootRun) {
  const toolCalls = findToolCalls(rootRun.outputs.response);
  const ok = EXPECTED.every((e) => toolCalls.includes(e));
  return { key: 'multi_tool_call_any_order', score: ok ? 1 : 0 };
}

await evaluate(predictSqlAgentMessages, {
  data: 'sql-agent-response',
  evaluators: [containsAllToolCallsAnyOrder],
  numRepetitions: 3,
});

生产：追踪与在线评估

开启追踪只要配环境变量，一行代码都不用改：

.env
LANGCHAIN_TRACING_V2=true
LANGCHAIN_API_KEY=ls__...
LANGCHAIN_PROJECT="learning-langchain"

之后每一次运行都会作为一条 trace（从输入到输出的完整步骤链）出现在 LangSmith 里，附带调用量、成功率、延迟、token 数和成本。

生产阶段和预生产的本质差别：没有标准答案。所以要换两种信号：

  • 用户反馈——点赞点踩、有没有复制走、有没有重问。最真实的信号。
  • LLM 裁判实时打分——无参考评估，可以顺便当毒性和提示注入的护栏。

此外还可以做分类打标：有标准标签就用启发式评估器算准确率，没有就用 LLM 裁判按你定义的标准打标（做情感分析、意图分布统计）。

最实用的一条建议

先小范围灰度。放给一小批 beta 用户，用他们的真实提问和真实错误来搭第一版评估数据集，再放大。这比闭门造车攒数据集有效得多。

小结

记住这个

目标是「没变差」不是「全对」

LLM 应用不存在 100% 通过率，所以基线对比比绝对分数重要。

记住这个

评估器从简单的开始

启发式 → 人工 → LLM 裁判。倒着来会得到一堆无法验证的分数。

记住这个

Agent 要分三层测

最终回答、单步决策、完整轨迹。只测第一层查不出问题在哪。

记住这个

线上错误必须回流

每个线上 bug 都该变成一条数据集样例，否则它还会再来一次。
