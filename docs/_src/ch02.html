第 2 章

RAG 上篇：为你的数据建索引

模型不知道你公司的年报，也不知道上周发生了什么。解决办法不是「重新训练」，而是在提问时把相关资料一起递过去。这一章做的就是前半段：把资料变成能被快速检索的形式。

读完这一章你会

  • 用自己的话解释「嵌入」和「余弦相似度」，而不只是会调 API
  • 把 txt / 网页 / PDF 加载进来，切成大小合适、语义完整的块
  • 用 PGVector 存取向量，并用索引 API 处理「文档更新了怎么办」
  • 知道朴素切分什么时候不够用，以及 MultiVector / RAPTOR / ColBERT 各解决什么

为什么要做这一切

LLM 有两个绕不过去的知识盲区：私有数据（本来就不在训练集里）和知识截止（训练完之后的事它不知道）。碰到这两类问题，模型不会说「我不知道」，它会一本正经地编——这就是幻觉。

最直接的修法：提问时把相关段落贴在问题旁边。但你不可能把整份 500 页年报贴进去（上下文窗口装不下，也贵），所以需要一套「按问题找出最相关的几段」的机制。这套机制的准备工作就叫索引（indexing），也叫摄取（ingestion）。

嵌入到底是什么

嵌入就是把一段文本变成一串数字。这是有损的（数字还原不回原文），所以我们总是把原文和向量一起存。换来的好处是：文本可以做数学运算了。

老办法：词袋（稀疏向量）

LLM 之前就有嵌入。最朴素的做法是把所有出现过的词列成一张表，每句话按词频计数：

词What a sunny day.Such bright skies today.I haven't seen a sunny day in weeks.
sunny101
day101
bright010
skies010

它能做关键词搜索和垃圾邮件分类，但有个致命弱点：它只认字，不认意思。「sunny day」和「bright skies」一个词都不重合，在这个模型眼里毫无关系。

新办法：语义嵌入（稠密向量）

现代嵌入模型输出的是几百到几千个浮点数，每一维都不为 0（所以叫「稠密」）。关键性质是：意思相近的文本，向量在空间里也靠得近。

★ 嵌入还能干什么

除了搜索，同一个向量还能做聚类（自动发现主题）、分类（归入已知标签）、推荐（找相似文档）、异常检测（找离群的）。第 3 章的语义路由、第 6 章的工具检索，用的都是这个能力。

第一步：加载成文本

Document Loader 的用法都一样：选加载器 → 传参数（路径/URL）→ load()。返回的是 Document 列表，每个有 page_content（正文）和 metadata（来源、页码等）。

第二步：切分

加载完的文档动辄十万字符，塞不进上下文窗口。要切。难点在于切开的同时不要把语义切断。

RecursiveCharacterTextSplitter 的策略很聪明：按重要性从高到低依次尝试分隔符——先按段落 \n\n 切，还太长就按行 \n 切，再不行按空格切。这样能最大限度沿着文本的自然结构下刀。

ch2/{py,js}/d-rec-text-splitter · e-rec-text-splitter-code
from langchain_text_splitters import Language, RecursiveCharacterTextSplitter

splitter = RecursiveCharacterTextSplitter(chunk_size=1000, chunk_overlap=200)
chunks = splitter.split_documents(docs)          # 输入 Document 列表

# 切代码：用该语言的关键字当分隔符，函数体不会被劈开
py_splitter = RecursiveCharacterTextSplitter.from_language(
    language=Language.PYTHON, chunk_size=50, chunk_overlap=0
)
py_docs = py_splitter.create_documents([PYTHON_CODE])  # 输入字符串列表

const pySplitter = RecursiveCharacterTextSplitter.fromLanguage('python', {

ⓘ split_documents vs create_documents

前者吃 Document 列表（来自加载器），元数据自动继承；后者吃字符串列表，可以用第二个参数手动传每条的元数据。搞混了会报类型错误。

第三、四步：嵌入并入库

嵌入模型有两个方法：embed_documents（批量，索引时用）和 embed_query（单条，检索时用）。能批量就批量，比逐条调快得多。

存的地方叫向量库。本书用 PGVector——它是 Postgres 的一个扩展，好处是你不用多维护一个数据库，业务表和向量表在同一个 Postgres 里。

先起一个带 pgvector 的 Postgres
docker run --name pgvector-container \
  -e POSTGRES_USER=langchain -e POSTGRES_PASSWORD=langchain \
  -e POSTGRES_DB=langchain -p 6024:5432 \
  -d pgvector/pgvector:pg16
ch2/{py,js}/i-pg-vector
import uuid

from langchain_community.document_loaders import TextLoader
from langchain_core.documents import Document
from langchain_openai import OpenAIEmbeddings
from langchain_postgres.vectorstores import PGVector
from langchain_text_splitters import RecursiveCharacterTextSplitter

connection = "postgresql+psycopg://langchain:langchain@localhost:6024/langchain"

raw = TextLoader("./test.txt", encoding="utf-8").load()
documents = RecursiveCharacterTextSplitter(
    chunk_size=1000, chunk_overlap=200
).split_documents(raw)

embeddings_model = OpenAIEmbeddings(model="text-embedding-3-small")

# 一行完成：建表 + 批量嵌入 + 写入
db = PGVector.from_documents(documents, embeddings_model, connection=connection)

print(db.similarity_search("古希腊哲学的关键人物有谁", k=4))

# 后续增删：自己给 id，才能更新或删除
ids = [str(uuid.uuid4()), str(uuid.uuid4())]
db.add_documents([
    Document(page_content="there are cats in the pond",
             metadata={"location": "pond", "topic": "animals"}),
    Document(page_content="ducks are also found in the pond",
             metadata={"location": "pond", "topic": "animals"}),
], ids=ids)

db.delete(ids=[ids[1]])
import { TextLoader } from '@langchain/classic/document_loaders/fs/text';
import { RecursiveCharacterTextSplitter } from '@langchain/textsplitters';
import { OpenAIEmbeddings } from '@langchain/openai';
import { PGVectorStore } from '@langchain/community/vectorstores/pgvector';

const connectionString = 'postgresql://langchain:langchain@localhost:6024/langchain';

const raw = await new TextLoader('./test.txt').load();
const splitter = new RecursiveCharacterTextSplitter({ chunkSize: 1000, chunkOverlap: 200 });
const docs = await splitter.splitDocuments(raw);

const model = new OpenAIEmbeddings({ model: 'text-embedding-3-small' });
const db = await PGVectorStore.fromDocuments(docs, model, {
  postgresConnectionOptions: { connectionString },
});

console.log(await db.similaritySearch('古希腊哲学的关键人物有谁', 4));

文档更新了怎么办：索引 API

真实场景里数据会变。天真的做法是「全部删掉重建」——但重新计算嵌入是要花钱花时间的，而且期间检索会断。

LangChain 的索引 API 用一个 RecordManager 记住每条文档的内容哈希 + 写入时间 + 来源 ID。再次索引时，它对比哈希：没变的跳过，变了的写新版并删旧版。

ch2/{py,js}/j-record-manager
from langchain_classic.indexes import SQLRecordManager, index
from langchain_core.documents import Document
from langchain_openai import OpenAIEmbeddings
from langchain_postgres.vectorstores import PGVector

connection = "postgresql+psycopg://langchain:langchain@localhost:6024/langchain"

vectorstore = PGVector(
    embeddings=OpenAIEmbeddings(model="text-embedding-3-small"),
    collection_name="my_docs", connection=connection, use_jsonb=True,
)
record_manager = SQLRecordManager("my_docs_namespace", db_url=connection)
record_manager.create_schema()

docs = [
    Document(page_content="there are cats in the pond", metadata={"source": "cats.txt"}),
    Document(page_content="ducks are also found in the pond", metadata={"source": "ducks.txt"}),
]

print(index(docs, record_manager, vectorstore,
            cleanup="incremental", source_id_key="source"))
# {'num_added': 2, 'num_updated': 0, 'num_skipped': 0, 'num_deleted': 0}

print(index(docs, record_manager, vectorstore,
            cleanup="incremental", source_id_key="source"))
# {'num_added': 0, ..., 'num_skipped': 2}   ← 没有重复计费

docs[0].page_content = "I just modified this document!"
print(index(docs, record_manager, vectorstore,
            cleanup="incremental", source_id_key="source"))
# {'num_added': 1, ..., 'num_deleted': 1}   ← 旧版被清掉
import { PostgresRecordManager } from '@langchain/community/indexes/postgres';
import { index } from '@langchain/classic/indexes';
import { OpenAIEmbeddings } from '@langchain/openai';
import { PGVectorStore } from '@langchain/community/vectorstores/pgvector';

const connectionString = 'postgresql://langchain:langchain@localhost:6024/langchain';

const vectorStore = await PGVectorStore.initialize(
  new OpenAIEmbeddings({ model: 'text-embedding-3-small' }),
  { postgresConnectionOptions: { connectionString }, tableName: 'test_langchain' }
);

const recordManager = new PostgresRecordManager('test_namespace', {
  postgresConnectionOptions: { connectionString },
  tableName: 'upsertion_records',
});
await recordManager.createSchema();

console.log(await index({
  docsSource: docs, recordManager, vectorStore,
  options: { cleanup: 'incremental', sourceIdKey: 'source' },
}));

索引优化：朴素切分不够用的三种情况

「切成 1000 字一块然后嵌入」是能跑的基线，但在几类文档上表现很差。书里给了三个方向。

① MultiVectorRetriever：拿来检索的和拿来回答的可以不是一个东西

关键洞察：适合被搜到的文本，和适合喂给模型的文本，不一定相同。一张财务表格直接嵌入，语义信号很弱（全是数字），但它的一段文字摘要语义很清晰。那就嵌入摘要、返回原表。

ch2/{py,js}/k-multi-vector-retriever
import uuid

from langchain_classic.retrievers.multi_vector import MultiVectorRetriever
from langchain_core.documents import Document
from langchain_core.output_parsers import StrOutputParser
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.stores import InMemoryStore
from langchain_openai import ChatOpenAI

# 1. 给每个块生成摘要（batch 会自动并发）
prompt = ChatPromptTemplate.from_template("Summarize the following document:\n\n{doc}")
llm = ChatOpenAI(model="gpt-4.1-mini", temperature=0)
summarize_chain = {"doc": lambda x: x.page_content} | prompt | llm | StrOutputParser()
summaries = summarize_chain.batch(chunks, {"max_concurrency": 5})

# 2. 摘要进向量库，原块进 docstore，用 doc_id 关联
id_key = "doc_id"
retriever = MultiVectorRetriever(vectorstore=vectorstore, docstore=InMemoryStore(), id_key=id_key)

doc_ids = [str(uuid.uuid4()) for _ in chunks]
retriever.vectorstore.add_documents([
    Document(page_content=s, metadata={id_key: doc_ids[i]})
    for i, s in enumerate(summaries)
])
retriever.docstore.mset(list(zip(doc_ids, chunks)))

# 3. 直接搜向量库 → 拿到短摘要；走 retriever → 拿到完整原块
print(len(retriever.vectorstore.similarity_search("chapter on philosophy", k=2)[0].page_content))
print(len(retriever.invoke("chapter on philosophy")[0].page_content))
import * as uuid from 'uuid';
import { MultiVectorRetriever } from '@langchain/classic/retrievers/multi_vector';
import { InMemoryStore } from '@langchain/core/stores';
import { Document } from '@langchain/core/documents';
import { RunnableSequence } from '@langchain/core/runnables';
import { StringOutputParser } from '@langchain/core/output_parsers';

const chain = RunnableSequence.from([
  { doc: (doc) => doc.pageContent },
  prompt,
  llm,
  new StringOutputParser(),
]);
const summaries = await chain.batch(docs, { maxConcurrency: 5 });

const idKey = 'doc_id';
const docIds = docs.map(() => uuid.v4());
const retriever = new MultiVectorRetriever({
  vectorstore: vectorStore,
  byteStore: new InMemoryStore(),
  idKey,
});
await retriever.docstore.mset(docs.map((d, i) => [docIds[i], d]));

console.log((await retriever.invoke('chapter on philosophy'))[0].pageContent.length);

② RAPTOR：给文档建一棵摘要树

有些问题问的是细节（「第 3 季度营收多少」），有些问的是全局（「整份报告的主要风险是什么」）。全局问题在任何单个 chunk 里都找不到答案。

RAPTOR 的做法：把块聚类 → 给每个簇写摘要 → 摘要再聚类再摘要，递归往上，形成一棵越往上越抽象的树。然后把树的所有层级和原始块一起索引。这样细节问题命中叶子，全局问题命中高层摘要。

③ ColBERT：不要把整段压成一个向量

普通嵌入把一整块文本压成一个定长向量，信息损失不小。ColBERT 改成每个 token 一个向量，检索时拿查询的每个 token 去和文档的所有 token 比，取每个查询 token 的最大相似度再求和。粒度细得多，代价是存储和计算都更贵。

⚠ 关于 ch2/py/l-rag-colbert.py

这个示例依赖 ragatouille，它会拉 PyTorch 和 transformers（几个 GB），且不支持 Windows 原生环境（需要 WSL2）。它不是后续章节的前置依赖，跑不起来可以直接跳过。

小结

记住这个

索引 = 加载 → 切分 → 嵌入 → 入库

四步各有一个 LangChain 组件对应，接口都统一，换实现不用改上下游。

记住这个

嵌入模型必须前后一致

索引和检索必须用同一个模型；不同模型的向量之间没有可比性，换模型要重建索引。

记住这个

k 不是越大越好

取太多会变慢、变贵，还会把无关内容塞进上下文，反而诱发幻觉。

记住这个

检索单元 ≠ 生成单元

这是 MultiVector / RAPTOR 共同的思路，也是提升 RAG 质量最有效的杠杆之一。
