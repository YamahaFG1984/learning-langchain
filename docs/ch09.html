生产架构：四块拼图

向量库：Supabase 的三段 SQL

Supabase 就是托管的 Postgres。开通后在 SQL 编辑器里依次跑这三段：

Supabase SQL 编辑器
-- ① 打开 pgvector 扩展
create extension vector;

-- ② 建文档表；1536 维对应 OpenAI 的嵌入模型，换模型要改这个数
create table documents (
  id bigserial primary key,
  content text,          -- 对应 Document.page_content
  metadata jsonb,        -- 对应 Document.metadata
  embedding vector(1536)
);

-- ③ 相似度检索函数：先按 metadata 过滤，再按余弦距离排序取前 N 条
create function match_documents (
  query_embedding vector(1536),
  match_count int default null,
  filter jsonb default '{}'
) returns table (
  id bigint, content text, metadata jsonb, embedding jsonb, similarity float
)
language plpgsql as $$
#variable_conflict use_column
begin
  return query
  select id, content, metadata, (embedding::text)::jsonb as embedding,
         1 - (documents.embedding <=> query_embedding) as similarity
  from documents
  where metadata @> filter
  order by documents.embedding <=> query_embedding
  limit match_count;
end;
$$;
★ 读懂那两个符号

<=> 是 pgvector 的余弦距离运算符（越小越像），所以相似度写成 1 - 距离。@> 是 JSONB 的「包含」运算符，用来做元数据过滤——正好对应第 3 章的 SelfQueryRetriever。

配置与本地调试

上线前需要一个 langgraph.json，告诉 Platform 你的图在哪：

ch9/{py,js}/langgraph.json
{
  "dependencies": ["."],
  "graphs": {
    "indexer": "./src/ingestion_graph/graph.py:graph",
    "retrieval_graph": "./src/retrieval_graph/graph.py:graph"
  },
  "env": "../../.env"
}

# graphs 的值格式：文件路径:变量名
# 这个变量必须是编译后的图（builder.compile() 的返回值）
# langgraph.json 要放在与图文件同级或更上层的目录
{
  "node_version": "20",
  "graphs": {
    "ingestion_graph": "./src/ingestion_graph/graph.ts:graph",
    "retrieval_graph": "./src/retrieval_graph/graph.ts:graph"
  },
  "env": "../../.env",
  "dependencies": ["."]
}

本地服务起来后，用 SDK 调用它，和调用线上部署完全一样：

ch9/{py,js}/demo
import asyncio

from langgraph_sdk import get_client


async def main():
    client = get_client(url="http://localhost:2024")   # 换成线上 URL 即可上生产

    thread = await client.threads.create(metadata={"user_id": "example_user"})

    async for event in client.runs.stream(
        thread_id=thread["thread_id"],
        assistant_id="retrieval_graph",          # 就是 langgraph.json 里的 key
        input={"query": "这份文档在讲什么？"},
        stream_mode="updates",
    ):
        print(event.event, event.data)


asyncio.run(main())
import { Client } from '@langchain/langgraph-sdk';

const client = new Client();          // 默认连 http://localhost:2024

const thread = await client.threads.create();

const streamResponse = client.runs.stream(thread.thread_id, 'retrieval_graph', {
  input: { query: '这份文档在讲什么？' },
  streamMode: 'updates',
});

for await (const chunk of streamResponse) {
  console.log(chunk.event, chunk.data);
}
↻ 1.x 变更（仓库中的 ch9 模板）
  • StateGraph(..., config_schema=X) → context_schema=X（from_runnable_config 读 config["configurable"] 的写法仍然有效）
  • from langchain.hub import pull → from langchain_classic.hub import pull
  • 修正了 retrieve_documents：make_retriever 是上下文管理器，必须用 with；且它接收的是 RunnableConfig 而不是配置对象
  • 修正了路由 schema：route: str = Literal[...] 写法有误，应为 route: Literal["retrieve", "direct"]

上线

  1. 把仓库推到 GitHub。
  2. LangSmith → Deployments → New Deployment（需要 Plus 套餐；也可以选自托管，但要自己维护 Postgres 和 Redis）。
  3. 用 GitHub OAuth 授权，选仓库和分支，填 langgraph.json 的路径。
  4. Development type 选 Production（约 500 req/s，高可用存储 + 自动备份）。
  5. 逐条填环境变量，凡是密钥都勾上 Secret。
  6. 提交，等构建完成，得到一个 revision。

之后每次改动点 New Revision。构建和部署日志在 Revisions → Deploy 里；因为和 LangSmith 打通，用量、错误率、延迟、token 成本都在同一个面板上看。

💡 LangGraph Studio

它是给 Agent 用的 IDE：可视化图结构、单次调用的完整轨迹、中途修改某个节点的输出再继续跑、编辑线程状态、触发人在环路。第 8 章讲的那些能力，Studio 给了图形界面。

安全清单

三条原则，配三个具体场景：

还要防滥用（也就是防账单爆炸）

第一道

账号验证

邮箱或手机验证，挡住脚本批量注册。

第二道

限流

中间件里统计每个用户近 X 分钟的请求数，超了就冷却或封禁。

第三道

提示注入护栏

假设用户会尝试诱导模型泄露数据或做无关的事。提示要写得具体且强约束，权限也要相应收紧。

小结

部署这一步真正的工作量不在「点部署按钮」，而在把本地代码改造成能被托管的形态：图必须是模块级可导入的变量，配置必须能从环境读，依赖必须写清楚，密钥必须不在代码里。langgraph.json 就是这份契约。

上线只是开始。下一章讲怎么知道它跑得好不好，以及怎么持续改进。
