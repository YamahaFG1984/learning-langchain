第 5 章

LangGraph 认知架构

同样的砖头，能砌成游泳池也能砌成房子——区别在图纸。这一章讲的就是 LLM 应用的图纸：把多少决策权交给模型，就决定了你在哪一层架构上。

读完这一章你会

  • 用「自主性阶梯」这把尺子给任何 LLM 应用定位
  • 说清楚自主性（agency）和可靠性（reliability）为什么互相拉扯
  • 用 LangGraph 实现链式架构和路由架构，并知道各自适合什么
  • 用 input_schema / output_schema 把内部状态和对外接口分开

自主性阶梯

衡量一个 LLM 应用「有多自主」，看三件事分别由谁决定：

  1. 每一步的输出内容由 LLM 决定（比如写一封回信的草稿）
  2. 下一步走哪条路由 LLM 决定（比如判断这封邮件该归档、回复还是转人工）
  3. 有哪些步可走由 LLM 决定（比如让 LLM 现场写代码执行一个你没预设的动作）

把这三条按「交给 LLM 的数量」排开，就得到了几种常见架构：

★ 一个具体的例子：邮件助手

假设你要做一个「替我读邮件」的助手，约束是：少打扰我，且绝不能替我发出我不会发的邮件。这两条约束直接决定了架构选择——第一条推着你往右（更自主），第二条拉着你往左（更可靠）。第 8 章专门讲怎么同时满足这两边。

架构 1：单次 LLM 调用

就是第 4 章那个 chatbot：START → chatbot → END。别小看它——Notion 的「总结」「翻译」，很多产品里的 AI 功能，本质上就是这个。

架构 2：链

多次 LLM 调用，顺序是你写死的。有人管这叫「流程工程」（flow engineering）。

书里的例子是一个 text-to-SQL 应用：第一步把自然语言变成 SQL，第二步再让一个模型用大白话解释这条 SQL 在干什么，好让不懂 SQL 的用户确认「这确实是我想问的」。

ch5/{py,js}/b-sql-generator
from typing import Annotated, TypedDict

from langchain_core.messages import HumanMessage, SystemMessage
from langchain_openai import ChatOpenAI
from langgraph.graph import END, START, StateGraph
from langgraph.graph.message import add_messages

model_low_temp = ChatOpenAI(model="gpt-4.1-mini", temperature=0.1)
model_high_temp = ChatOpenAI(model="gpt-4.1-mini", temperature=0.7)


class State(TypedDict):
    messages: Annotated[list, add_messages]   # 内部：对话历史
    user_query: str                             # 输入
    sql_query: str                              # 输出
    sql_explanation: str                        # 输出


class Input(TypedDict):
    user_query: str


class Output(TypedDict):
    sql_query: str
    sql_explanation: str


generate_prompt = SystemMessage("你是数据分析师，根据用户问题生成 SQL 查询。")


def generate_sql(state: State) -> State:
    user_message = HumanMessage(state["user_query"])
    res = model_low_temp.invoke([generate_prompt, *state["messages"], user_message])
    return {"sql_query": res.content, "messages": [user_message, res]}


explain_prompt = SystemMessage("你是数据分析师，用大白话向用户解释 SQL 查询。")


def explain_sql(state: State) -> State:
    # state["messages"] 里已经有上一步的问题和 SQL 了
    res = model_high_temp.invoke([explain_prompt, *state["messages"]])
    return {"sql_explanation": res.content, "messages": res}


builder = StateGraph(State, input_schema=Input, output_schema=Output)
builder.add_node("generate_sql", generate_sql)
builder.add_node("explain_sql", explain_sql)
builder.add_edge(START, "generate_sql")
builder.add_edge("generate_sql", "explain_sql")
builder.add_edge("explain_sql", END)

graph = builder.compile()

print(graph.invoke({"user_query": "每个产品的总销售额是多少？"}))
# {'sql_query': 'SELECT product_name, SUM(...) ...', 'sql_explanation': '这条查询会…'}
# 注意 messages 没有出现在结果里 —— 被 output_schema 挡住了
import { HumanMessage, SystemMessage } from '@langchain/core/messages';
import { ChatOpenAI } from '@langchain/openai';
import {
  StateGraph, Annotation, messagesStateReducer, START, END,
} from '@langchain/langgraph';

const modelLowTemp = new ChatOpenAI({ model: 'gpt-4.1-mini', temperature: 0.1 });
const modelHighTemp = new ChatOpenAI({ model: 'gpt-4.1-mini', temperature: 0.7 });

const annotation = Annotation.Root({
  messages: Annotation({ reducer: messagesStateReducer, default: () => [] }),
  user_query: Annotation(),
  sql_query: Annotation(),
  sql_explanation: Annotation(),
});

async function generateSql(state) {
  const userMessage = new HumanMessage(state.user_query);
  const res = await modelLowTemp.invoke([generatePrompt, ...state.messages, userMessage]);
  return { sql_query: res.content, messages: [userMessage, res] };
}

async function explainSql(state) {
  const res = await modelHighTemp.invoke([explainPrompt, ...state.messages]);
  return { sql_explanation: res.content, messages: res };
}

const graph = new StateGraph(annotation)
  .addNode('generate_sql', generateSql)
  .addNode('explain_sql', explainSql)
  .addEdge(START, 'generate_sql')
  .addEdge('generate_sql', 'explain_sql')
  .addEdge('explain_sql', END)
  .compile();
↻ 1.x 变更

书上写的是 StateGraph(State, input=Input, output=Output)。这两个参数在 LangGraph 0.5 已改名为 input_schema= / output_schema=，旧名还能用但会打弃用警告。

★ 为什么要分 Input / Output schema

因为「内部要传的东西」和「对外暴露的东西」通常不一样。上例里 messages 是两个节点之间传递上下文用的中间状态，用户不需要看到。分开之后，输入校验更严，输出更干净，中间状态还能通过 stream() 观察到。

架构 3：路由器

再往上一级：让 LLM 决定下一步走哪。

场景：一个医疗助手，背后有两个知识库——病历库和保险 FAQ 库。往提示里塞无关内容只会拉低效果，所以每个问题应该只查一个库。谁来判断该查哪个？LLM。

★ LLM 之前是怎么做的

训一个分类器：手工标一批「问题 → 应该查哪个库」的数据，提取特征，训练模型。光是攒数据集就够呛。LLM 因为已经理解语言，几乎不需要样本就能当这个分类器用。这是 LLM 最被低估的用法之一。

ch5/{py,js}/c-multi-rag
from typing import Annotated, Literal, TypedDict

from langchain_core.documents import Document
from langchain_core.messages import HumanMessage, SystemMessage
from langchain_core.vectorstores.in_memory import InMemoryVectorStore
from langgraph.graph import END, START, StateGraph
from langgraph.graph.message import add_messages


class State(TypedDict):
    messages: Annotated[list, add_messages]
    user_query: str
    domain: Literal["records", "insurance"]     # ← 路由决策存这里
    documents: list[Document]
    answer: str


router_prompt = SystemMessage(
    """判断用户问题应该路由到哪个领域。有两个可选：
- records：病历，包含诊断、治疗、处方
- insurance：保险 FAQ，包含保单、理赔、承保范围
只输出领域名。"""
)


def router_node(state: State) -> State:
    user_message = HumanMessage(state["user_query"])
    res = model_low_temp.invoke([router_prompt, *state["messages"], user_message])
    return {"domain": res.content, "messages": [user_message, res]}


# 条件边函数：读状态，返回下一个节点的名字（不是返回状态更新！）
def pick_retriever(state: State) -> Literal["retrieve_medical_records", "retrieve_insurance_faqs"]:
    if state["domain"] == "records":
        return "retrieve_medical_records"
    return "retrieve_insurance_faqs"


builder = StateGraph(State, input_schema=Input, output_schema=Output)
builder.add_node("router", router_node)
builder.add_node("retrieve_medical_records", retrieve_medical_records)
builder.add_node("retrieve_insurance_faqs", retrieve_insurance_faqs)
builder.add_node("generate_answer", generate_answer)

builder.add_edge(START, "router")
builder.add_conditional_edges("router", pick_retriever)     # ← 分流
builder.add_edge("retrieve_medical_records", "generate_answer")  # ← 汇合
builder.add_edge("retrieve_insurance_faqs", "generate_answer")
builder.add_edge("generate_answer", END)

graph = builder.compile()

for chunk in graph.stream({"user_query": "新冠治疗在我的保险范围内吗？"}):
    print(chunk)
function pickRetriever(state) {
  return state.domain === 'records'
    ? 'retrieve_medical_records'
    : 'retrieve_insurance_faqs';
}

const graph = new StateGraph(annotation)
  .addNode('router', routerNode)
  .addNode('retrieve_medical_records', retrieveMedicalRecords)
  .addNode('retrieve_insurance_faqs', retrieveInsuranceFaqs)
  .addNode('generate_answer', generateAnswer)
  .addEdge(START, 'router')
  .addConditionalEdges('router', pickRetriever)
  .addEdge('retrieve_medical_records', 'generate_answer')
  .addEdge('retrieve_insurance_faqs', 'generate_answer')
  .addEdge('generate_answer', END)
  .compile();
⚠ 条件边函数返回的是节点名

这是新手最容易搞混的地方：普通节点返回「状态更新字典」，条件边函数返回「下一个节点的名字字符串」（或 END）。返回错了会报节点找不到。

另外建议给 add_conditional_edges 传第三个参数（可能的目标节点列表），这样画出来的图才会显示所有分支。

小结

架构LLM 决定特征典型场景
LLM 调用输出内容一个节点总结、翻译、分类
链每步输出内容固定顺序的多个节点先生成后校验、先起草后润色
路由器+ 走哪条路条件边，路径多条但有限多数据源 RAG、意图分发
Agent（下一章）+ 循环几次、何时停有环，步数不定开放式任务

选型建议：从最右边往左试。先看单次 LLM 调用够不够，不够再加一步，还不够再加路由。每往右一格，你就多买了一份能力，也多付了一份不可预测性。
