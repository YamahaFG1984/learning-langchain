第 03 章

RAG 下篇：与你的数据对话

索引建好了，现在的问题变成：用户随口一问，怎么保证捞上来的正好是该捞的？这一章的六个技巧，全都在回答这一个问题。

读完这一章你会

  • 写出一个 20 行的完整 RAG 问答链，并知道每一行在做什么
  • 用四种查询变换手法（改写 / 多查询 / RAG-Fusion / HyDE）处理「用户问得很烂」
  • 用逻辑路由和语义路由把问题分发到正确的数据源
  • 把自然语言转成元数据过滤条件或 SQL，并知道 text-to-SQL 的安全底线

RAG 的三个阶段

把上一章和这一章连起来看，RAG 就三步：索引（离线）→ 检索（每次提问）→ 生成（每次提问）。

最小可用版本长这样。注意 @chain / RunnableLambda 把三步封成一个函数——这个「把多步打包成一个可调用单元」的习惯，在后面每一章都会用到。

ch3/{py,js}/a-basic-rag 
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.runnables import chain
from langchain_openai import ChatOpenAI

# db 来自第 2 章：PGVector.from_documents(...)
retriever = db.as_retriever(search_kwargs={"k": 2})

prompt = ChatPromptTemplate.from_template(
    """只根据以下上下文回答问题：
{context}

问题：{question}
"""
)
llm = ChatOpenAI(model="gpt-4.1-mini", temperature=0)


@chain
def qa(question):
    docs = retriever.invoke(question)                       # ② 检索
    formatted = prompt.invoke({"context": docs, "question": question})
    return llm.invoke(formatted)                            # ③ 生成


print(qa.invoke("古希腊哲学史上的关键人物有哪些？").content)
import { ChatPromptTemplate } from '@langchain/core/prompts';
import { RunnableLambda } from '@langchain/core/runnables';
import { ChatOpenAI } from '@langchain/openai';

const retriever = db.asRetriever({ k: 2 });

const prompt = ChatPromptTemplate.fromTemplate(
  `只根据以下上下文回答问题：
{context}

问题：{question}
`
);
const llm = new ChatOpenAI({ model: 'gpt-4.1-mini', temperature: 0 });

const qa = RunnableLambda.from(async (question) => {
  const docs = await retriever.invoke(question);
  const formatted = await prompt.invoke({ context: docs, question });
  return await llm.invoke(formatted);
});

console.log((await qa.invoke('古希腊哲学史上的关键人物有哪些？')).content);

书里用的 retriever.get_relevant_documents(q) 已废弃，统一改成 retriever.invoke(q)（所有组件同一个接口，见第 1 章）。ChatOpenAI(model_name=…) 也统一成 model=。

查询变换：用户问得烂怎么办

基础 RAG 有个隐含假设：用户的问题本身就是一个好的检索查询。现实里不是。试试这个：

一个被噪声淹没的问题
"今天我起床刷了牙，然后坐下看新闻。结果忘了锅上还煮着东西。
 古希腊哲学史上有哪些关键人物？"

→ 基础 RAG 的回答：Based on the given context, there is no information provided.

检索器把整段话（包括刷牙和煮饭）一起嵌入了，向量被噪声带偏。解法统称查询变换：先把用户的问题改造成更适合检索的形式，再去检索。四种手法按「抽象程度」排列：

Rewrite-Retrieve-Read

最简单：加一次 LLM 调用，把用户原话改写成一句干净的检索词，用改写后的去检索，但生成时仍然用原问题（用户想要的答案是针对原问题的）。

ch3/{py,js}/b-rewrite 
rewrite_prompt = ChatPromptTemplate.from_template(
    """为下面这个问题写一个更适合搜索引擎的查询词，以 '**' 结尾。
问题：{x}
答："""
)

def parse_rewriter_output(message):
    return message.content.strip('"').strip("**")

rewriter = rewrite_prompt | llm | parse_rewriter_output


@chain
def qa_rrr(question):
    new_query = rewriter.invoke(question)          # ① 改写
    docs = retriever.invoke(new_query)             # ② 用改写后的检索
    formatted = prompt.invoke({"context": docs, "question": question})  # ③ 用原问题生成
    return llm.invoke(formatted)
const rewritePrompt = ChatPromptTemplate.fromTemplate(
  `为下面这个问题写一个更适合搜索引擎的查询词，以 '**' 结尾。
问题：{question}
答：`
);

const rewriter = rewritePrompt
  .pipe(llm)
  .pipe((m) => String(m.content).replaceAll('"', '').replaceAll('**', ''));

const qa = RunnableLambda.from(async (question) => {
  const newQuery = await rewriter.invoke({ question });
  const docs = await retriever.invoke(newQuery);
  const formatted = await prompt.invoke({ context: docs, question });
  return await llm.invoke(formatted);
});

Multi-Query：一个问题拆成五个

让 LLM 从不同角度改写出 5 个版本，并行检索（这就是 batch 存在的意义），再把结果去重合并。

ch3/{py,js}/c-multi-query 
perspectives_prompt = ChatPromptTemplate.from_template(
    """你是一个 AI 助手。请针对用户的问题生成 5 个不同角度的版本，
用来从向量库中检索相关文档。每行一个，不要编号。
原问题：{question}"""
)

def parse_queries_output(message):
    return message.content.split("\n")

query_gen = perspectives_prompt | llm | parse_queries_output


def get_unique_union(document_lists):
    # 用正文当 key 去重：字典同一个 key 只会留一条
    deduped = {doc.page_content: doc for sub in document_lists for doc in sub}
    return list(deduped.values())

# retriever.batch 会并行跑 5 条查询，返回「列表的列表」
retrieval_chain = query_gen | retriever.batch | get_unique_union
const queryGen = perspectivesPrompt
  .pipe(llm)
  .pipe((m) => String(m.content).split('\n'));

const retrievalChain = queryGen
  .pipe(retriever.batch.bind(retriever))
  .pipe((documentLists) => {
    const deduped = {};
    documentLists.flat().forEach((doc) => { deduped[doc.pageContent] = doc; });
    return Object.values(deduped);
  });

RAG-Fusion：合并时讲究排序

Multi-Query 的并集是「无序的一堆」。RAG-Fusion 多做一步 RRF（倒数排名融合）：一篇文档在多条查询里排名都靠前，就该排到最前面。

ch3/{py,js}/d-rag-fusion 
def reciprocal_rank_fusion(results: list[list], k=60):
    fused_scores, documents = {}, {}
    for docs in results:                     # 每条查询的结果列表
        for rank, doc in enumerate(docs):     # rank 就是它在这条列表里的位置
            key = doc.page_content
            if key not in fused_scores:
                fused_scores[key], documents[key] = 0, doc
            fused_scores[key] += 1 / (rank + k)
    ordered = sorted(fused_scores, key=lambda d: fused_scores[d], reverse=True)
    return [documents[key] for key in ordered]


retrieval_chain = query_gen | retriever.batch | reciprocal_rank_fusion
function reciprocalRankFusion(results, k = 60) {
  const fusedScores = {}, documents = {};
  results.forEach((docs) => {
    docs.forEach((doc, rank) => {
      const key = doc.pageContent;
      if (!(key in fusedScores)) { fusedScores[key] = 0; documents[key] = doc; }
      fusedScores[key] += 1 / (rank + k);
    });
  });
  return Object.entries(fusedScores)
    .sort((a, b) => b[1] - a[1])
    .map(([key]) => documents[key]);
}

const retrievalChain = queryGen
  .pipe(retriever.batch.bind(retriever))
  .pipe(reciprocalRankFusion);

书里的一个笔误

原书 JS 版 reciprocalRankFusion 里写的是 documents[key] = 0，应该是 documents[key] = doc，否则最后返回的是一堆 0。仓库里已经修好。

HyDE：先编一个假答案

问题通常很短，文档通常很长——两者在向量空间里天然不太像。HyDE 的思路是：让 LLM 先「幻觉」出一段像模像样的答案，用这段假文档去检索。假答案的事实可能是错的，但它的用词和文风更接近真文档，检索命中率更高。

ch3/{py,js}/e-hyde 
from langchain_core.output_parsers import StrOutputParser

prompt_hyde = ChatPromptTemplate.from_template(
    "请写一段文字来回答这个问题。\n问题：{question}\n段落："
)

generate_doc = prompt_hyde | ChatOpenAI(model="gpt-4.1-mini", temperature=0) | StrOutputParser()

# 假文档 → 检索器（检索器会自动把它嵌入并搜索）
retrieval_chain = generate_doc | retriever
const generateDoc = promptHyde.pipe(llm).pipe((msg) => msg.content);

const retrievalChain = generateDoc.pipe(retriever);

查询路由：该去哪个库找

如果你有多个数据源（Python 文档库、JS 文档库、SQL 数据库…），先得决定去哪儿找。两种做法：

ch3/{py,js}/f-router（逻辑路由） 
from typing import Literal

from pydantic import BaseModel, Field


class RouteQuery(BaseModel):
    """把用户问题路由到最相关的数据源。"""

    datasource: Literal["python_docs", "js_docs"] = Field(
        ..., description="根据问题涉及的编程语言，选择最相关的数据源"
    )


llm = ChatOpenAI(model="gpt-4.1", temperature=0)
structured_llm = llm.with_structured_output(RouteQuery)

prompt = ChatPromptTemplate.from_messages([
    ("system", "你是路由专家。根据问题涉及的编程语言，把它路由到对应的数据源。"),
    ("human", "{question}"),
])
router = prompt | structured_llm

result = router.invoke({"question": "为什么这段 Python 代码不工作……"})
print(result.datasource)   # python_docs


def choose_route(result):
    # 注意：不做精确相等比较，而是转小写后做子串匹配——对 LLM 的偶发偏差更宽容
    if "python_docs" in result.datasource.lower():
        return "chain for python_docs"
    return "chain for js_docs"
import { z } from 'zod';

const routeQuery = z
  .object({
    datasource: z
      .enum(['python_docs', 'js_docs'])
      .describe('根据问题涉及的编程语言，选择最相关的数据源'),
  })
  .describe('把用户问题路由到最相关的数据源。');

const structuredLlm = new ChatOpenAI({ model: 'gpt-4.1', temperature: 0 })
  .withStructuredOutput(routeQuery, { name: 'RouteQuery' });

const router = prompt.pipe(structuredLlm);
console.log(await router.invoke({ question }));   // { datasource: 'python_docs' }

一条通用原则

「对 LLM 输出的随机性保持宽容」贯穿整本书。上面用子串匹配而不是 ==，就是一个具体体现。凡是拿 LLM 输出去做程序分支的地方，都值得留一点容错。

查询构造：自然语言 → 查询语言

「1980 年有哪些外星人电影？」这句话里其实混了两种东西：「外星人」是语义（要靠向量检索），「1980 年」是结构化条件（应该做精确过滤）。把它们分开处理，效果远好于全部丢给向量检索。

文本 → 元数据过滤（SelfQueryRetriever）

# 描述你的元数据长什么样——这段描述会被写进提示词

import { AttributeInfo } from '@langchain/classic/chains/query_constructor';

  llm,
  vectorStore,

文本 → SQL

结构化数据大多在关系型数据库里。让 LLM 写 SQL 有两个提准确率的关键：把每张表的 CREATE TABLE 语句和几行示例数据放进提示，以及给几个「问题 → SQL」的示例。

ch3/{py,js}/i-sql-example 
from langchain_classic.chains import create_sql_query_chain
from langchain_community.tools import QuerySQLDatabaseTool
from langchain_community.utilities import SQLDatabase

db = SQLDatabase.from_uri("sqlite:///Chinook.db")
llm = ChatOpenAI(model="gpt-4.1", temperature=0)

write_query = create_sql_query_chain(llm, db)   # 自然语言 → SQL
execute_query = QuerySQLDatabaseTool(db=db)      # 执行 SQL

chain = write_query | execute_query
print(chain.invoke({"question": "一共有多少员工？"}))
import { createSqlQueryChain } from '@langchain/classic/chains/sql_db';
import { SqlDatabase } from '@langchain/classic/sql_db';
import { QuerySqlTool } from '@langchain/classic/tools/sql';
import { DataSource } from 'typeorm';

const datasource = new DataSource({ type: 'sqlite', database: 'Chinook.db' });
const db = await SqlDatabase.fromDataSourceParams({ appDataSource: datasource });

const writeQuery = await createSqlQueryChain({ llm, db, dialect: 'sqlite' });
const executeQuery = new QuerySqlTool(db);

console.log(await writeQuery.pipe(executeQuery).invoke({ question: '一共有多少员工？' }));

上线之前必须做的三件事

「让 LLM 生成 SQL 然后直接执行」在生产环境里是危险操作。至少要做到：

  1. 只读账号——数据库用户不具备 INSERT/UPDATE/DELETE/DROP 权限。
  2. 最小表权限——只授权你确实希望被查询的那几张表。
  3. 查询超时——防止一条昂贵的查询把数据库拖垮。

小结

这一章的六个技巧看起来五花八门，其实回答的是四个问题：

问题手法代价
用户问得不好Rewrite / Multi-Query / RAG-Fusion / HyDE每次多 1 次 LLM 调用
数据分散在多处逻辑路由 / 语义路由1 次 LLM 或 1 次嵌入调用
查询语言不是自然语言SelfQuery / text-to-SQL1 次 LLM 调用 + 安全风险
索引本身不够好第 2 章的 MultiVector / RAPTOR / ColBERT索引时间与存储

关键工程习惯：把每个技巧封装成一条独立的 retrieval_chain。这样你能一行代码换掉检索策略，也能把它们组合起来（比如「先路由，再多查询，再 RRF」）。

到这里，你的应用能查资料了，但它还是「问一次答一次」——不记得你上一句说了什么。下一章解决记忆。
