第 8 章

榨干 LLM 的实用模式

自主性和可靠性天生互相拉扯。这一章讲的四类技巧，目的都是同一个：把这条取舍曲线整体往外推——同样的可靠性下拿到更多自主性，或者反过来。

读完这一章你会

  • 用「前沿曲线」这个模型解释为什么不存在「又快又稳又自主」的架构
  • 选对 stream_mode，让高延迟变得可以忍受
  • 用 interrupt / authorize / resume / edit / fork 五种人在环路手法接管运行中的图
  • 为「用户连发两条消息」这种情况选一个合适的处理策略

前沿曲线

先建立一个共同的心智模型。横轴是自主性（它能自己干多少事），纵轴是可靠性（你能多信任它的输出）。第 5–7 章的每种架构都落在这条曲线上的某一点。

技巧一：结构化输出

要求模型按预定义的格式输出，输出就更可预测。三种实现方式，with_structured_output 会替你挑最合适的那个：

方式原理保证程度
提示在提示里「请你输出 JSON」只是建议，任何模型都能用，但不保证
工具调用把 schema 当成一个函数签名发给模型较强，需要模型经过工具调用微调
JSON mode模型侧强制解码出合法 JSON保证是合法 JSON，但不保证符合你的 schema
ch8/{py,js}/a-structured-output
from langchain_openai import ChatOpenAI
from pydantic import BaseModel, Field


class Joke(BaseModel):
    setup: str = Field(description="笑话的铺垫")
    punchline: str = Field(description="笑话的包袱")


# 低温度对结构化输出很关键：减少「跑偏」导致的校验失败
model = ChatOpenAI(model="gpt-4.1", temperature=0).with_structured_output(Joke)

print(model.invoke("Tell me a joke about cats"))
# Joke(setup="Why don't cats play poker in the wild?", punchline='Too many cheetahs.')
import { ChatOpenAI } from '@langchain/openai';
import { z } from 'zod';

const joke = z.object({
  setup: z.string().describe('笑话的铺垫'),
  punchline: z.string().describe('笑话的包袱'),
});

const model = new ChatOpenAI({ model: 'gpt-4.1', temperature: 0 })
  .withStructuredOutput(joke);

console.log(await model.invoke('Tell me a joke about cats'));
💡 传 Pydantic / Zod 对象的额外好处

schema 会被用于两次：转成 JSON Schema 发给模型，以及校验模型的返回。如果模型给了不合规的东西，你拿到的是一个校验错误，而不是一份悄悄坏掉的数据。

技巧二：流式中间输出

架构越复杂，延迟越高——这是没法回避的。但「等 10 秒什么都看不到」和「10 秒里一直有进展」是完全不同的体验。

LangGraph 的 stream() 支持多种模式，选对了能同时解决「进度可见」和「结果可用」两件事：

ch8/{py,js}/b-streaming-output
from agent import QUESTION, build_graph   # 第 6 章「工具太多」那个图

graph = build_graph()
input = {"messages": [HumanMessage(QUESTION)]}

# ① 看进度：每个节点完成就产出一条 {节点名: 状态更新}
for c in graph.stream(input, stream_mode="updates"):
    print(c)

# ② 看内容：逐 token 输出图内任何一次 LLM 调用
for chunk, metadata in graph.stream(input, stream_mode="messages"):
    if chunk.content:
        print(chunk.content, end="", flush=True)
const input = { messages: [new HumanMessage(QUESTION)] };

// ① 看进度
for await (const c of await graph.stream(input, { streamMode: 'updates' })) {
  console.log(c);
}

// ② 看内容（逐 token）
for await (const [chunk] of await graph.stream(input, { streamMode: 'messages' })) {
  if (chunk.content) process.stdout.write(String(chunk.content));
}
↻ 1.x 变更

书里用 astream_events(input, version="v2") 再手工筛 on_chat_model_stream 事件来做逐 token 输出。现在直接用 stream_mode="messages" 就行，简洁得多。astream_events 仍然可用，但已不是首选。

技巧三：人在环路

越自主的架构，越需要一个「人能插手」的口子。LangGraph 因为把状态集中管理，这件事变得很自然。所有人在环路手法的前提都是：编译时挂了 checkpointer。

authorize：调工具前先问一句

最常用的一种：在指定节点执行前自动停下，让人确认。典型用于「这条 SQL 真的要执行吗」「这封邮件真的要发吗」。

ch8/{py,js}/d-authorize · e-resume
from langgraph.checkpoint.memory import InMemorySaver

graph = build_graph(checkpointer=InMemorySaver())
config = {"configurable": {"thread_id": "1"}}

# ① 跑到「即将进入 tools 节点」就停
async for c in graph.astream(input, config, interrupt_before=["tools"]):
    print(c)

# ② 看看它想干什么
state = await graph.aget_state(config)
print("停在：", state.next)                                   # ('tools',)
print("待执行的工具调用：", state.values["messages"][-1].tool_calls)

# ③ 批准了就用 None 输入继续；None = 「接着上次的往下走」
async for c in graph.astream(None, config):
    print(c)
import { MemorySaver } from '@langchain/langgraph';

const graph = buildGraph({ checkpointer: new MemorySaver() });
const config = { configurable: { thread_id: '1' } };

// ① 跑到 tools 前停下
for await (const c of await graph.stream(input, { ...config, interruptBefore: ['tools'] })) {
  console.log(c);
}

// ② 检查
const state = await graph.getState(config);
console.log(state.next, state.values.messages.at(-1).tool_calls);

// ③ 批准，继续
for await (const c of await graph.stream(null, config)) console.log(c);

edit state：不满意就改了再继续

ch8/{py,js}/f-edit-state · g-fork
# —— 改写模型选的搜索词，再放行 ——————————————————
state = graph.get_state(config)
last = state.values["messages"][-1]

edited = last.model_copy(deep=True)
edited.tool_calls[0]["args"]["query"] = "Calvin Coolidge age at death"

# add_messages 遇到相同 id 会「替换」而不是「追加」——这里正是靠这个性质
graph.update_state(config, {"messages": [edited]})

for c in graph.stream(None, config):
    print(c)


# —— 回到历史上的某个检查点重开一条分支 ————————————
history = list(graph.get_state_history(config))   # 最新的在前，最旧的在后
for i, s in enumerate(history):
    print(i, "next:", s.next)

result = graph.invoke(None, history[2].config)   # 从 history[2] 重跑，原轨迹保留
const state = await graph.getState(config);
const last = state.values.messages.at(-1);
last.tool_calls[0].args.query = 'Calvin Coolidge age at death';
await graph.updateState(config, { messages: [last] });

for await (const c of await graph.stream(null, config)) console.log(c);

// fork：回到历史检查点
const history = await Array.fromAsync(graph.getStateHistory(config));
await graph.invoke(null, history[2].config);

技巧四：用户连发两条怎么办

LLM 慢，所以用户很可能在上一条还没跑完时就又发了一条（发现打错字了、改主意了）。这叫 double texting，有五种处理策略：

策略做法优点缺点
拒绝正在跑就不收新输入最简单把并发问题甩给调用方
独立处理开一个新 thread 单独跑可无限扩展两次运行无法关联，UI 上很怪
排队跑完当前再处理新的结果与到达时刻无关，很确定队列可能无限增长；新输入可能已经过时
打断丢弃当前，立刻处理新的延迟低，不会输出过时结果仍是串行；保留部分状态时容易留下非法中间态
分叉合并并行跑，最后合并状态理论上最优状态必须可无冲突合并（CRDT 之类）
⚠ 「打断」的隐藏陷阱

OpenAI 的接口要求：一条请求调用工具的 AIMessage 后面必须紧跟对应的 ToolMessage。如果恰好在这中间打断并保留了部分状态，下一次调用会直接被 API 拒绝。所以要么防御性地清理中间状态，要么等当前节点跑完再断。

好消息：这几种策略 LangGraph Platform 已经内置实现（第 9 章的 multitask_strategy 参数），自己部署时才需要手写。

小结

对应目标

结构化输出 → 降方差

把自由文本变成有 schema 的数据，下游代码才敢用。

对应目标

流式输出 → 抵消延迟

不减少总耗时，但把「等待」变成「观看」。

对应目标

人在环路 → 用监督换自主

让高自主架构在关键点上重新变得可控。

对应目标

并发策略 → 保证体验一致

决定用户抢跑时应用怎么表现，别让它自由发挥。
